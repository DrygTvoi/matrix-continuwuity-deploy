# bridges/

Optional mautrix bridges. Enabled by `BRIDGES` / `COMPOSE_PROFILES` in `.env`
(the interactive `setup.sh` can generate all of them).

Each bridge gets:

- `config.yaml` — generated by the bridge image, then patched by
  `scripts/patch_bridge_config.py` to point at `continuwuity:8008` and SQLite.
- `registration.yaml` — generated by the bridge image on its second start.
  Register it with Continuwuity by running `./scripts/register-bridges.sh`
  after creating the first (admin) account.

Services listen only on the internal Docker network; their login UI is exposed
through Caddy at `https://bridge.<domain>/<bridge>/` (or `BRIDGE_HOST` when a
custom hostname is configured).

| Bridge | Service | Bot user | Notes |
|---|---|---|---|
| Telegram | `mautrix-telegram` | `@telegrambot:<domain>` | needs `TELEGRAM_API_ID` / `TELEGRAM_API_HASH` |
| Discord | `mautrix-discord` | `@discordbot:<domain>` | log in with a user token or QR |
| WhatsApp | `mautrix-whatsapp` | `@whatsappbot:<domain>` | needs a separate phone number |
| Signal | `mautrix-signal` | `@signalbot:<domain>` | needs a separate phone number |

After registration, start the bridge containers with `docker compose up -d`,
then open a direct chat with the bot and send `login`.

Telegram, WhatsApp and Signal have end-to-bridge encryption enabled
(`encryption.allow: true`). The Discord bridge does not support it, so keep
Discord portal rooms unencrypted.

The generated example values (`example.com`, `foobar`, `as_token:foobar`) are
disabled by the patcher. Do not re-enable them.
